# Feature map

Every feature Callboard will ever have, on one page, mapped to the gate that decides when it gets built. Each ID traces to [`PRD.md`](PRD.md) (A1–A11 §8.2, B1–B8 §8.3, G1–G6 §9); tables to [`DATA_MODEL.md`](DATA_MODEL.md); rationale to [`decisions/`](decisions/).

**B9, B10 and P4 are the exceptions** — they have no PRD entry, because they did not exist when it was written. B9 and B10 came out of building B6 and B7 and finding what those actually needed: an audit export the board can read without learning which judge is which, and a kill switch for a leaked link. **P4 came out of somebody asking to see the product**, which is a different way to find a missing row: every screen existed and there was no way in to any of them that was not a credential pasted into an address bar. Their rationale is in [ADR-0008](decisions/0008-judge-scores-are-de-identified.md), [ADR-0011](decisions/0011-nothing-mints-a-link.md) and [ADR-0022](decisions/0022-a-link-is-exchanged-for-a-cookie.md).

This map **sequences; it does not authorize.** The PRD argues against building (§13). Nothing below the gate starts before three founding partners sign — building it to win a signature spends the whole selling window on boards that have committed nothing. This is the build order for the moment the gate clears, not a to-do list that ignores it.

**Status**

| | |
|---|---|
| **Live** | shipped, deployed **and migrated** at `callboard-eta.vercel.app`, and the beat walked there |
| **Designed** | everything short of that — from specced-in-`docs/` to written, tested and merged but never yet exercised against production. **Which of those a row is, the row says in its own words.** |
| **Won't build** | the tarpit — stays in the tools that already do it |

**Two words for a range that has five states, and that is now a choice rather than an oversight.** The states are *written, reachable, migrated, usable, correct*, and four of the defects recorded below lived in the gaps between them. A fifth status word was tried for the gap and folded back out: a word is the thing a reader's eye slides past, and every one of those four defects was caught by somebody reading a row's **prose** and noticing it claimed something the product could not do. So `Designed` covers everything short of `Live`, and the sentence carries the distinction. **Moving a row to `Live` is an act performed against production, never a line edited in the same commit as the feature** — that half was never about the vocabulary.

Counts: **20 live** — 10 (Module B) + 7 (Module A) + 2 (Adjacent) + 1 (Platform). Everything else reads `Designed`, and **eleven** of those rows — **A4**'s materials half, **A10**, **A11**, **ADJ·2**, **C1**, **C2**, **P4**, and the Gita's **G1**, **G2**, **G3** and **G6** — are code that exists, passes its tests, is merged, and has never been run against the deployed database. It said *three* until August 2026, naming only the comms tier; each of the others was added to the map without anybody re-counting the line above. **A count in prose is a second definition of the table below it**, which is the same defect this page keeps recording, one altitude up.

**"Live" means a board can reach it.** That sentence had to be added because it was not being kept: A7 and A8 were marked Live for a day while `recordPayment`, `advanceDeposit` and `listDepositsForBoard` had no caller anywhere in the repo — a library the product never executed, and A9's screen with nothing linking to it. Meanwhile `setTeamStatus` generated real charges, so a board using it watched every team it accepted become a permanent debtor. A status word that means "the code exists" is a status word this map cannot be trusted with.

**And "reach it" means on the deployed database, which is the second half and it was false for nineteen days.** From **July 13 to August 1, 2026** every row below marked Live in Module A and ADJ·3 was unreachable: Neon `main` sat at migration `0006` while Vercel served code expecting `0010`, so `/register` and `/c/[org]/[comp]` returned HTTP 500 and the roster and money screens read four tables that did not exist. A1 shipped on July 13 with the migration that broke it; the money spine and ADJ·3 landed on top of an already-broken demo and nobody found out, because the fix for the *first* defect above — checking that code has callers — says nothing about whether the schema underneath it arrived.

Merging is not deploying, and deploying is not migrating. `db:doctor` now counts applied migrations against `drizzle/meta/_journal.json` and prints which compute it just checked, because the preflight that would have caught this on day one was run against `dev` the whole time and printed the same green line.

**And the third form of the same defect is a row that is reachable, deployed, migrated — and holds a fact nobody can state.** Fixed on **August 2, 2026**. `teams.rooms` had one writer in the repo, `src/db/seed.ts`: neither the registration form nor the roster screen could set it, so every team that ever applied through the product was permanently *"hotel: not billed — room count unknown"* and a comp charging $140 a room could not charge one of them. `syncCharges` ran only from `setTeamStatus`, so a status transition was the only thing that re-ran the fee schedule and a late fee whose date passed was billed to nobody. `comps.status` gated the public form and only the seed wrote it, so closing registration meant reseeding the comp — which reissues every token. `payments.reconciled_at` had no writer at all. Each screen worked, each test passed, and the product quietly billed the wrong number. **A status word that means "a board can reach it" is not yet a status word that means "a board can use it";** what closes that gap is running the beat end to end against the deployed host, which is what found all four.

**And the first form came back, inside the phase that was written to close it.** Found on **August 2, 2026**, by auditing P1 the way the money spine had just been audited. Three defects, all the original shape — *written, with nothing reaching it*: `/my/[comp]` resolves a `captain` membership **by name**, and the landing page linked all three roles at it, so a board member who accepted an invitation, signed in and clicked their own comp was told it did not exist — in the same commit as a code comment claiming they "sees the comp listed and is told where their own way in is." `resolveLiaisonActor` had **no caller anywhere**, while the invite form offered Liaison in its dropdown, so a board could mint a credential whose entire journey ended on a page that refused to load — which is [ADR-0011](decisions/0011-nothing-mints-a-link.md)'s own failure arriving through the door [ADR-0016](decisions/0016-accounts-for-people-who-stay-links-for-people-who-visit.md) opened. And `memberships.revoked_at` was read by every membership filter and **written by nothing**, so P1 shipped a way to put somebody on a comp and no way to take them off — the identical omission ADR-0011 was written about, in a phase whose own decision made sessions rows specifically so that credentials could be killed. All three are closed: the landing page routes by role and says what a board link is still for, `INVITABLE_ROLES` is the one definition of what may be handed out and `inviteAction` reads it as a rule rather than markup, and a board can remove a person from the People screen. The lesson is not new, which is the point: **an audit found these, and no test did**, because the tests were written around the same assumption the code was.

**And the fourth form is a row that is reachable, deployed, migrated, usable — and quietly wrong about money.** Found on **August 2, 2026**, by auditing the three fixes above rather than by anything failing. A7 was `Live` and a refund moved **no number anywhere**: the deposit charge stayed owed, `paid` still counted the returned cash, and the team read *settled* — the exact reconciliation gap PRD §13 promises to take to `$0`, reintroduced by the feature written to close it. `releaseAllocation` had shipped complete, transactional and audited with **no caller**, so a mis-typed attribution was permanent and the ledger's own error message pointed at an instrument that did not exist. And `db:doctor` could not see either: `deposit_events` was missing from the tables it checks, so a deposit that ended twice was invisible to the preflight whose whole job is to find that shape. **Each of the four is the same defect one layer further in** — written, reachable, migrated, usable — and the layer after "usable" is *correct*, which only an audit or a treasurer finds.

## Phase 00 — Shipped · the scoring demo · **Live**

Module B (Tabulation), PRD §8.3. Judges score from any phone; the math runs itself; results lock into a snapshot that reproduces the next day. This is the sales instrument — the one thing PRD §8.4 says to build before selling.

| ID | Feature | Detail | Source |
|---|---|---|---|
| **B1** | Per-comp rubric configuration | Criteria, weights (integer basis points), normalization, tiebreakers are data, authored in a config file — not hardcoded. Fusion and classical rubrics differ entirely. | `rubrics`, `rubric_criteria` |
| **B2** | Score from any phone, no install | A signed link; the raw 32-byte token lives only in the URL, its sha256 in the database. The form is plain HTML and submits without JavaScript. | ADR-0003, `judge_assignments` |
| **B3** | Auto-normalization | Raw mean, per-judge z-score, or negated mean rank — per rubric. A zero-spread judge contributes 0, never NaN. | `normalize.ts` |
| **B4** | Deduction entry | Time penalties applied to every judge's per-team total *before* normalization — the only well-defined choice when the aggregate is standard deviations. | `deductions` |
| **B5** | Live tabulation + tiebreaks | Standings update every 2s. Ties broken by an ordered list (criterion, head-to-head Copeland, highest single judge); a surviving tie is surfaced, never silently picked. A score naming a team that is not on the roster is ignored — `teams` is the roster of record, and a team that withdrew must not keep placing with the scores it was already given. | ADR-0009, `rank.ts` |
| **B6** | Locked, attributed audit trail | Locking freezes inputs, rubric, results into one row. A correction **replays that frozen row** and appends its deduction — it never re-reads the tables, so nothing written after the lock can enter it — and every lock and override carries a person's name. A score that lands after the lock counts in no run, and the board is told. Closed July 2026. | ADR-0004, ADR-0007, `tab_runs` |
| **B7** | Blind judging, both directions | A judge's projection of a team never selects its name; the board's projection of a judge *beside a score* never selects theirs. Blindness is a property of the return type both ways — a compile error to leak. Closed July 2026. | ADR-0008, `scope.ts` |
| **B8** | Emcee sheet + per-team feedback | A printable placement sheet the emcee reads from directly. Each team's feedback file carries its placement, its deduction and the reason, and each judge's note under `Judge N` — and **no scores**. One file per team, so a forward cannot leak a rival's notes. | ADR-0008, `export/feedback.ts` |
| **B9** | Board score breakdown | The board's own audit export: every judge's score on every criterion, from the frozen snapshot, under `Judge 1 / Judge 2`. Lets a board spot a rogue judge without learning which of its judges it was. | `export/scores.ts` |
| **B10** | Revocable links, both kinds | A leaked judge *or board* link can be killed from the board screen. Board revocation outlives the lock, because a board link is the one that can still override a locked result — and the last live link is refused, because nothing mints a replacement. | ADR-0011, `board_assignments` |

## ▓▓▓ The founding-partner gate · PRD §13 ▓▓▓

**This line was drawn to hold until the gate cleared. It has been crossed ten times**, each at the founder's direction: A1 and A2 in July 2026, ADJ·3 on July 31, the money spine (A3, A6–A9) on the same day, on August 1 the work that made A7/A8/A9 reachable rather than merely written, and on August 2 the work that made A7 and A8 *arithmetically true* rather than merely reachable — a refund that moves the money, an attribution that can be taken back, and a preflight that can see both ([ADR-0015](decisions/0015-a-refund-moves-the-money.md), migration `0011`) — and on the same day **P1 accounts**, which is the sixth and the largest, because it is the first crossing that builds a *platform* rather than a feature: it was authorized as the foundation of the whole remaining map (schedules, liaisons, comms, reminders, the team portal), every one of which needs to reach one specific human. **The seventh was C2's engine on August 3** and the **eighth its callers on August 4–5** — A7's receipts, ADJ·2's feedback delivery, an invitation that sends itself, and the board's first announcement. Those two are one crossing split in half by a week, and worth counting separately for what the split showed: the engine shipped complete and audited with nothing queueing into it, which is the fifth time this repo has built a working subsystem the product could not reach, and the second half is what fixed it. **The ninth was the product shell on August 6** ([ADR-0022](decisions/0022-a-link-is-exchanged-for-a-cookie.md)) — a front door, a dashboard, and board access moved onto the accounts P1 built, which is the sentence `src/app/page.tsx` had been carrying as a promise since P1 shipped: *"until P1 migrates board access onto accounts."* It built no new capability and is a crossing anyway, because it is the first work here aimed at somebody *using* the product rather than at the record being right. **The tenth was C1 on August 16** — liaison and volunteer coordination, which this file's own scope-discipline list named as a thing not to build without being asked, and which was asked for. It is the first crossing that *removes* a table (`comp_roles`, dropped rather than used) and the first to close a defect that was live in the repo rather than one already recorded: `resolveLiaisonActor` had zero call sites from P1 onward, so a role existed that nothing could open. **Three things about this count, all recorded rather than resolved.** `CLAUDE.md` said *eight* until August 17, 2026 while this paragraph said nine and then ten — a crossing landed and only one of the two files was updated, so the repo's two summaries of its own history disagreed, by one and then by two. And **#27 (A4's materials half) and #28 (A11) landed after the ninth and are not separately counted here**, which is a choice and not an oversight: both are Module A work built ahead of the gate, and whether they are crossings of their own or merely more of the sixth is the founder's call, not this file's. It is left visible so the number cannot drift again without somebody noticing. The gate is recorded as crossed rather than moved, and PRD §12's own name for what was authorized here is worth quoting: *"scope creep to an ERP — eleven committees tempt eleven modules, the everything-app failure mode."* The gate itself has not moved — Track 1 is **0/10 conversations and 0/3 signatures** — so the line is recorded here as breached rather than redrawn, because a line that moves to wherever the code got to is not a line.

The fourth crossing is the one worth reading twice, because it is not the same kind as the other three. It built no new feature: it discovered that `recordPayment`, `advanceDeposit` and `listDepositsForBoard` had **no caller anywhere in the repo**, and that the screen A9 shipped was linked from no page. Three status words on this map were false, and the asymmetry made them worse than incomplete — the owed side was reachable, so a board using the product watched every team it accepted become a permanent debtor. The lesson is about this map rather than about the build order: **a status column that records what was written rather than what a board can reach is not a record of anything.**

What remains genuinely gated is named in each phase heading below, and the largest piece of it is Stripe (A5–A5c). The selling window is **August**; boards for spring 2027 are forming now. Nothing on this page moves Track 1.

The founding season is **free** ($0; $300 from 2027–28), so a "yes" costs a board nothing and is worth nothing. A signature is a named person, a comp date, **their roster / fee schedule / last season's payment records**, and a **written $300 line in the budget they hand their successors**. Those are the things a board can only give if it means it.

**A1 and A2 were built in July 2026, before the gate cleared**, at the founder's direction. | ID | Feature | Status | Detail | Needs | Source |
|---|---|---|---|---|---|
| **A1** | Configurable registration form | **Live** | Per comp: team info, roster size, audition-video link, waiver acknowledgment — authored as data in the comp config, like the rubric. The public form is the first page with no `Actor`; the projection is the scope. What it collects, the board can *see*: the audition link, the captain, and the waiver are on the roster screen, because accepting a team is a decision made about its application. | **A2** | Application → acceptance → waitlist | **Live** | The status lifecycle as one total transition map. It is the **captain's** page and only theirs, which is what the landing page failed to honour for a day: linking a board member at it sent them to a `notFound()`, because `resolveTeamActor` asks for a `captain` membership by name and that is exactly the property making a fourth window safe. **The materials half is now written and merged, and has not been walked on production, so this row does not move.** It is final music, an emergency contact, and a stated dancer count, filed by the captain on the page that already shows what they owe and read by the board on the roster screen. ## Phase 02 — v1 · Module A · Payments · **A6–A9 live · A5x gated**

The treasurer's pain, and why the ledger disagrees with the bank by ~$5,000 today. Callboard **never holds funds and never touches the org's tax status** — and today it does not move money at all: every `payments` row is hand-entered, on a rail we record and do not route. Every amount is integer cents.

**The split is the point.** The ~$5k gap is closed by the **ledger** — obligations, payments, allocations, roster joined to money — which works perfectly well on a hand-entered `rail: 'venmo'` row. **Stripe (A5–A5c) buys ingestion, not correctness**, and stays gated: building card rails before a board says it wants them is guessing, and [ADR-0005](decisions/0005-stripe-connect-standard-never-hold-funds.md) remains *designed, not implemented*. A6–A9 were authorized July 31, 2026, ahead of the gate; the decisions they rest on are [ADR-0002](decisions/0002-money-as-cents-and-allocations.md) and [ADR-0014](decisions/0014-the-allocation-counter.md).

| ID | Feature | Status | Detail | Needs | Source |
|---|---|---|---|---|---|
| **A5** | Stripe Connect (Standard) | Designed | Each comp connects its own account; funds settle directly to the org, which owns payouts and the 1099. Callboard orchestrates and reconciles — never a money transmitter. | — | ADR-0005 |
| **A5a** | ACH-first routing | Designed | Lumps ($600–$2,160) route over ACH (0.8%, cap $5) by default; cards stay for small/last-minute items. Collapses a ~$11.5k season from ~$250 to ~$60–80. | A5 | PAYMENTS.md |
| **A5b** | Nonprofit card rate | Designed | Support the verified-nonprofit rate (2.2% + $0.30) in connected-account setup. Most host orgs qualify. | A5 | PRD A5b |
| **A5c** | Optional surcharge pass-through | Designed | Per comp, pass the processing fee to the paying team, disclosed at checkout (≤3%). The honest answer to "won't we net less than we charge?" | A5 | PRD A5c |
| **A6** | Fee schedule engine | **Live** | Per-dancer, per-room, deposit, late fee → each team's exact total. Pure and ESLint-fenced, so a bill is a function of the schedule and the roster and nothing else; `asOf` is passed in, because a module that read the clock would bill differently on Tuesday. A component the comp does not charge produces **no line**, not a $0 one, and an unknown room count produces a stated gap rather than a $0 hotel charge a treasurer would believe. **A board can re-run it**, which it could not until Aug 2, 2026: `syncCharges` fired only from `setTeamStatus`, so nothing regenerated charges once a team's status settled and the late fee — whose entire definition is *the date passed* — was never billed to anybody. Safe to click twice by construction, not by care, because `planCharges` keys on `(teamId, kind)`. **What a late fee should mean is still open**: as specified it lands on every billable team once `lateAfter` passes, including one that paid in November, and whether it should key off a balance instead is a question for a founding partner rather than a guess in the engine. | — | `fee_schedules`, `charges`, `src/lib/fees/` |
| **A7** | Refund state machine | **Live** | A refund is *not* a negative payment — negative gross would make `allocated_cents <= gross_cents` uninterpretable, and that ceiling is what ADR-0014 bought. So a deposit's fate is its own append-only chain, `deposit_events`, modelled on `tab_runs`: one row per transition ordered by `seq`, state is `max(seq)`'s row, and `deposit_events_terminal_unique` refuses a **second ending** — a double-clicked refund button being the realistic way a deposit is returned twice. `refund_failed` is deliberately not terminal: a bounced ACH return is retryable, and calling it an ending would strand money in a state the product cannot leave. A board drives it from the deposit table on the comp's money screen, whose buttons come from the machine's own `allowedFrom` so there is no second list to drift. **And on August 2, 2026 it started moving money**, which for a day it did not ([ADR-0015](decisions/0015-a-refund-moves-the-money.md)): a refund wrote an event and an audit row and changed no number anywhere, so the deposit charge stayed owed, `paid` still counted the cash, and the team read *settled* while the money sat in its account rather than the org's — PRD §13's `$0` reconciliation error, missed by the feature written to close it. `refunded` now voids the obligation, releases its allocations and records `payments.refunded_cents`, so owed and paid fall together; `forfeited` moves nothing, because the org keeps money the team owed. The chain is keyed on `(comp_id, team_id)` rather than on the charge, because `planCharges` voids and re-inserts a charge on any amount change and *a deposit ends once* was true of a row instead of a deposit — and a **dropped** team's deposit is now reachable, where the roster window's live-charges filter used to hide it at exactly the moment the question is asked. **Receipts are built**, and they are two templates rather than one: `payment.receipt` when money arrives, and `deposit.returned` when a deposit goes back. A refund is *not* a negative payment, so a returned deposit is not a receipt with a minus sign in it — and the number its notice carries is the one that did **not** move, because `refunded` voids the obligation and releases its allocations together and a captain must not read the return as a fresh bill. There is deliberately **no forfeit notice**: a forfeit moves no money and is a board keeping something a team expected back, which is a sentence a person should say rather than a template. Both are queued *after* the transaction rather than inside it — a comms failure must never roll back money that genuinely arrived, which would be this product's own headline defect caused by the feature announcing it. | A6 | ADR-0014, ADR-0015, `deposit_events` |
| **A8** | Fee-aware ledger | **Live** | gross / fee / net as three integers per payment, allocated to charges. A $100 deposit arriving as $97.01 is a recorded cost, not a hole; a treasurer types gross and fee and NCSU's $2,160 unbundles across three obligations on the entry form. Money can also be attached **after** it arrived (`allocatePayment`), because a deposit paid to hold a slot lands while the team is `applied` and has no obligations yet — without that, the entry form would bake in a lump that could never be attributed. Voiding a charge releases what was attached to it, so a dropped team's payment stays findable rather than pointing at a row nobody can read. The second and last sanctioned `withTransaction` caller, and the third reader of `violatedConstraint` — a money constraint is a sentence for a treasurer. Every row is hand-entered on a rail we record and do not route.
