## Scope discipline

The PRD gates the real v1 on three signed founding partners (§13) — the founding season is free, so the signature, not a deposit, is the costly signal. Track 1 is still **0/10 conversations and 0/3 signatures**, and no line of code moves it.

The repo contains the judge-scoring demo (Module B, complete), registration (A1), the application → acceptance → waitlist lifecycle (A2), the public comp page (ADJ·3), the money spine (A3, A6–A9), real accounts (P1), and the comms engine with its callers (C2, A10, A7's receipts, ADJ·2, announcements, the invitation). **The gate has been crossed ten times**, each at the founder's direction, starting July 12, 2026. (It said *eight* here while FEATURE_MAP.md said nine, and *nine* while FEATURE_MAP.md said ten — twice a crossing landed and only one of the two files was updated. FEATURE_MAP.md enumerates all ten and is the record; this is the summary, and a summary that drifts twice is a summary worth distrusting.) All of it is ahead of the gate and against the PRD's own advice. That is recorded, not endorsed; PIPELINE.md still says building Module A to win a signature spends the selling window on boards that have committed nothing, and Track 1 has not moved off 0/10 and 0/3.

**Merged is not `Live`, and the comms tier is where that currently bites.** A10, ADJ·2 and C2 are written, tested and merged, and **nothing has ever been sent from the deployed database** — sending is opt-in on `RESEND_API_KEY` and `COMMS_FROM`, which production does not have. FEATURE_MAP.md reads `Designed` for all three on purpose.

**FEATURE_MAP.md's status column is the record of what actually exists**, not this paragraph. Check it before assuming a table is there.

**A document may not assert that a spike was run unless the spike is a tracked file.** This repo has a written rule against code with no caller and needed one against a *claim with no code*: `ARCHITECTURE.md` and ADR-0006 both said a `db.batch` + `SET LOCAL` spike had been run and settled P3's hardest question, and until August 16, 2026 there was no `set_config`, no `current_setting` and no `SET LOCAL` anywhere in `src/`, `drizzle/` or `e2e/`, `db.batch` had no callers, and `*.local.ts` is gitignored. Every earlier instance of this defect was at least *visible* — somebody could read the function nothing called. This one was findable only by grepping for something that is not there, which is why it survived two documents and a plan. A probe belongs in `e2e/`, where CI re-runs it and the claim keeps its witness — which is where it now is, as `e2e/rls-spike.spec.ts`, and it found the belief right and the *written mechanism* wrong: the GUC carries and does not leak, but `SET LOCAL app.comp_id = $1` is refused by Postgres and `set_config(name, value, true)` is the only parameterizable form.

**The line now holds at Stripe.** Do not build **Stripe, Connect, card rails, webhooks, or the Gita** without being asked — they are designed in `docs/` and deliberately unimplemented. The comms engine came off this list on August 3–5, 2026 when it was built and given callers, and **C1's liaison coordination came off it on August 16, 2026** — `comp_roles` dropped, `assignments` built, a liaison given a screen and `INVITABLE_ROLES` widened to match, all at the founder's direction and recorded rather than endorsed; **G5's push-on-change did not**, because it is the Gita's trigger rather than the engine's, and neither did a second self-serve anything. [ADR-0005](docs/decisions/0005-stripe-connect-standard-never-hold-funds.md) is still *designed, not implemented*, and the question under it is not a technical one: the ledger closes the ~$5,000 gap of PRD §14 on hand-entered `rail: 'venmo'` rows, so routing buys ingestion and a known `fee_cents`, not correctness. Whether a student board wants card rails is a question for the founding partners, not for this file. If a change starts pulling one of them in, stop and say so.

The fee schedule the money spine is built against is **the repo's own best guess** — `per_dancer_cents`, `per_room_cents`, `deposit_cents`, `late_fee_cents`, `late_after`, taken from DATA_MODEL.md and INTAKE.md and calibrated on Mayuri 2026. No founding partner has handed one over. It is deliberately a *config* shape rather than a hardcoded one, so the first real schedule that arrives is data, not a migration — but a schedule that does not fit those five fields is a signal about the design, not a bug in the parser.

## Invariants

**Money is integer cents.** Columns are `*_cents integer`. Never float, never `numeric` read into a JS `number` for arithmetic. `payments` splits `gross_cents` / `fee_cents` / `net_cents`; a payment attaches to charges through `payment_allocations`, never directly. This is not fussiness — see the $97.01 deposit and the $2,160 lump in PRD §14.

The rest of this section is the contract the money spine is built to. It was decided before the code, so that the code cites it rather than the other way round; the files it names land with migration `0009`.

**A team's balance is `owed - paid`, and `paid` is every cent that arrived** — never the sum of allocations to its *live* charges. Allocations answer *what was this money for*; the balance answers *does this team owe anything*. Deriving the second from the first loses every payment whose charge was later voided, so a team that paid, dropped and came back gets billed the whole amount again with its money still in the org's account. That is the failure this product is sold against, reintroduced by the product; `e2e/money.spec.ts` is what caught it and is what keeps it caught.

**A deposit ends once, it belongs to a team, and an index is what says so.** `deposit_events` is the `tab_runs` chain applied to a refund: append-only, ordered by `seq`, state is `max(seq)`'s row. `deposit_events_terminal_unique` is partial over `('refunded','forfeited')`, so a second ending is unrepresentable — a double-clicked refund button is how a deposit gets returned twice, and the read and the insert are two acts. `refund_failed` is **not** terminal: a bounced ACH return is retryable, and an ending there would strand money in a state the product cannot leave.

The index is keyed on **`(comp_id, team_id)`, not on `charge_id`** ([ADR-0015](docs/decisions/0015-a-refund-moves-the-money.md)), because keyed on the charge it enforced exactly what it said and what it said was the wrong noun: `planCharges` voids and re-inserts a charge whenever its amount changes, so a `depositCents` edit or a drop-and-reinstate minted a fresh id with an empty chain and an already-refunded deposit became refundable again. For the same reason `listDepositsForBoard` does **not** filter to live charges — a drop voids them, and a dropped team's deposit is the one a board most needs to act on.

**A refund moves the money; a forfeit does not.** A refund is never a negative `payments` row, because negative gross makes the allocation ceiling uninterpretable — it is `payments.refunded_cents`, and `paid` is `sum(gross_cents - refunded_cents)`, one definition, in `listRosterForBoard`. `refunded` voids the deposit charge and releases its allocations, so `owed` and `paid` fall together and the balance does not move; `forfeited` touches nothing, because the org keeps money the team owed and every number is already right. That asymmetry is the model rather than an omission. **What a board should do with a dropped team's deposit is still a board's question** — both endings are one click and neither is a default.

**A payment is never allocated past what was paid, and the database is what says so** ([ADR-0014](docs/decisions/0014-the-allocation-counter.md)). The invariant spans rows, so a `CHECK` cannot see it and a transaction would only protect the code that remembers to ask. Instead `payments.allocated_cents` carries the sum, `CHECK (allocated_cents <= gross_cents)` constrains it, and it moves only by `UPDATE ... SET allocated_cents = allocated_cents + $n` — one atomic read-modify-write that takes its own row lock, so racing allocators serialize and the check fires in the same statement. **Move the counter before inserting the allocation**, because that decides which constraint fires on a race and therefore which sentence a treasurer reads.

The residual is deliberate and must stay visible: the database enforces `allocated <= gross`, **not** `allocated = sum(live allocations)`. Anything writing an allocation without moving the counter creates a disagreement — so `db:doctor` reports drifting payments by id, exactly as it reports a forked chain. Three more refusals travel with it, each because the alternative produces a wrong number rather than an error: **`voided_at`, never `DELETE`** (deleting a charge destroys the record of what a payment was *for*); **`amount_cents > 0`, never negative** (a revision is a void plus an insert); and **`net = gross - fee` is a `CHECK`, not a generated column** (a generated column *supplies* the right answer, so a bank import that disagrees imports cleanly and the discrepancy vanishes — and the $5k gap is made of discrepancies nobody was shown). Their names have one definition, `MONEY_CONSTRAINTS` in `src/db/schema/money.ts`, for `CHAIN_INDEXES`' reason.

**`src/lib/fees/schedule.ts` is pure, for `src/lib/tabulation/`'s reason and under the same ESLint fence.** What a team owes must be reproducible from the schedule and the roster alone; `asOf` is passed in, because `late_after` is a date and a module that reads the clock bills a different number on Tuesday.

**A pure engine still needs a hand on it, and for three weeks the fee engine had one that only a status transition could reach.** `syncCharges` was called from `setTeamStatus` and nowhere else, so nothing re-ran the schedule once a team settled — and a late fee, whose whole definition is *the date passed*, was billed to nobody. Two paths call it now, both the roster's transaction: `setTeamBilling` when a dancer or room count is stated, and `regenerateCharges` across the billable roster. **What a late fee should mean is deliberately unsettled**: today it lands on every billable team once `lateAfter` passes, including one that paid in November. Whether it should key off a balance is a founding partner's question, and the engine must not answer it by guess. Idempotency lives in the pure `planCharges`, keyed on `(teamId, kind)` among live charges to match `charges_live_kind_unique` by construction — so regenerating twice with no roster change is provably a no-op, and the test needs no database. `BILLABLE_STATUSES` has one definition, beside `SCOREABLE_STATUSES` and `ANNOUNCEABLE_STATUSES` in `src/db/schema/teams.ts`. **All three are equal today and none may alias another**: they answer *who is billed*, *who is ranked* and *who is written to*, and the day a comp bills at `applied` is the day the tabulator would start ranking applicants and an applicant would be sent the parking instructions. `ANNOUNCEABLE_STATUSES` is the newest and its own reason for existing is `dropped`: telling a team that withdrew where to park is the kind of thing a board never lives down.

**`src/lib/tabulation/` is pure.** No imports from `src/db/`, no `Date.now()`, no randomness. It takes `TabulationInput` and returns `TabulationResult`. This is what makes locked results reproducible a day later, and reproducibility is the thing being sold. Nothing new goes into `TabulationInput` without a reason that survives `reproducibility.test.ts` — `judge_notes` stays out for exactly this reason.

This is **enforced by ESLint**, not by discipline: `eslint.config.mjs` carries a zone over `src/lib/tabulation/**` banning `@/db`, `drizzle-orm`, `Date.now()`, `new Date()` and `Math.random()`. It had to be. `reproducibility.test.ts` only catches an impurity that *changes the result* — a clock read that happens not to is invisible to it, and stays invisible until the day it isn't. If you add a rule to `no-restricted-syntax` there, **re-declare the shared selectors**: a later flat-config block replaces that rule rather than merging into it, so the enum and class bans would quietly stop applying to the one directory that most needs them.

**A database error is read by its `constraint`, never by its message.** `violatedConstraint` in `src/db/errors.ts` is the one place that digs the name out of the cause chain, because drizzle wraps the driver error and its own `message` is the failed SQL. Three callers read it and mean three different things by it: `lockAction` treats a chain index as a **refusal** — there must not be a second root — `apply` treats `teams_comp_bid_code_unique` as a **retry**, because `nextBidCode` is a read-then-insert, registration day is the whole circuit applying at once, and the losing applicant did nothing wrong; and the ledger reads a `MONEY_CONSTRAINTS` name as **a sentence for a treasurer**, which is why the allocation counter moves *before* the allocation row is inserted — that choice decides which constraint fires on a race, and therefore which sentence a person reads. Same mechanism, three remedies; what they share is that none may guess from the message text. The registration form is the one page with no `Actor` behind it, and `Failed query: insert into "teams" ...` is not a thing to show a stranger.

**Append, never mutate.** Scores are immutable after a lock, with no exception and no unlock. A post-lock correction is an attributed `deductions` row plus a re-tabulation, written as a new `tab_runs` row with `supersedes_id` and a reason; the superseded row keeps its own frozen inputs. `audit_log` gets a row for every write that touches scores, locks, or overrides.

**A correction replays the snapshot; it does not re-read the world.** `lockResults` builds `TabulationInput` from the live tables **only for the first lock**. An override takes the superseded run's frozen `inputs` and `config` and appends only the deductions its caller wrote — otherwise anything landing between the lock and the correction (a judge who lost the race with the lock button, a rubric weight edited after) enters the corrected result silently, and *nothing can detect it*: each run reproduces from its own row, so both verify while describing different worlds. Reproducibility is a property of one row; continuity is a property of the pair, and only `e2e/override.spec.ts` reads it. New deductions are passed in, never diffed out of the table, because `DeductionInput` has no id and no timestamp — which is also what keeps `TabulationInput` unchanged. The consequence is deliberate and must stay visible: a score landing after the lock enters **no run, ever**, and `scoresOutsideChain` is what says so on the board.

**A `teamId` on a form is a claim.** The rule is one line: **a `teamId` is resolved against the scoped read that produced the form it arrived on.** That read is the check — comp scope and status filtering both come free from its own `where`, which is what stops the check from becoming a second definition of "which teams count".

There are three windows over teams, because they answer different questions, and **nine** write paths resolve against whichever one produced their form:

| Window | Write paths |
|---|---|
| `listTeamsForJudge` → `resolveTeamForJudge` | `submitScores`, `submitNote` |
| `listTeamsForBoard` → `resolveTeamForBoard` | `addDeductionAction`, `overrideAction` |
| `listRosterForBoard` → `resolveRosterTeamForBoard` | `setTeamStatus`, `setWaitlistRank`, `setTeamBilling`, `setShowOrder`, `moveInShowOrder` |

Two more answer questions that are not about which teams count, and each is argued below:

| Window | Write paths |
|---|---|
| `ownTeamForCaptain` | `submitMaterials` |
| `listDutiesForLiaison` → `resolveDutyForLiaison` | `acknowledgeDutyAction`, `completeDutyAction` |

**G1 added the eighth and ninth and no window** ([ADR-0023](docs/decisions/0023-the-draw-is-a-column-not-a-table.md)): `RosterTeamView` already carries `performanceOrder`, so *which team dances third* asks no new question about which teams count. `docs/DATA_MODEL.md` designed a `show_order` table and it was **not built** — it is `teams.performance_order` with extra steps, a column that existed since `0000`, was already read by both scoring windows, and had no writer in the product at all. `comp_roles`' lesson from the other direction.

`setTeamBilling` is the seventh and not a fourth window, for the reason A3 was not: `rosterSize` and `rooms` are already on `RosterTeamView`, so stating them asks no new question about which teams count. **Four** comp-scoped writes deliberately resolve **nothing**, because their subject is the actor's own comp rather than a row in it: `setCompStatus`, `regenerateCharges`, `sendAnnouncementAction` and `sendFeedbackAction` take scope from `actor.compId`, which is what the link resolved to. A write with no id on its form has no claim to check; that is not an exemption from the rule, it is the rule finding nothing to do. The two comms ones are worth reading as confirmation rather than as an addition: *tell everybody who is coming* and *send every placed team its notes* are questions about a comp, and both answer them by filtering a window that already exists (`listRosterForBoard`, and the frozen run) rather than by asking a new one.

**A3 widened the third window; it did not add a fourth.** `listRosterForBoard` now carries each team's live `charges` and its `balance`, because "roster and payment status, one record" is that window's own question with money attached — money changes the columns, not the `where`. A `chargeId` arriving on a form resolves one level down the same read (`team.charges.find(...)`), which keeps the rule's sentence literally true and is *stronger* than a WHERE clause: the array holds only this comp's, this team's, live charges, so another team's charge and a voided one are refused by the same `find`.

**Two derived reads resolve their own ids the same way, and neither is a fourth window.** `listDepositsForBoard` is `listRosterForBoard` with each team's deposit chain attached, so `advanceDeposit`'s `teamId` resolves through it; `listPaymentsForBoard` carries each payment's live allocations, so `releaseAllocation`'s `allocationId` resolves one level down that. Both inherit comp scope from the read they are built on, which is the rule working rather than an exception to it — and the allocation array holds only live rows, so an already-released one is refused by the same `find` that refuses another comp's.

**There is now a fifth window, and both the fourth and the fifth were argued rather than assumed.** The rule was never *never add one* — it is *do not add one casually*, and the bar is a genuinely new question. `ownTeamForCaptain` has one: the three original windows all answer *which teams count for this board or this judge*, and none can answer *what does **my** team owe* without being handed a `teamId` to trust. What makes it safe is that it takes no id from a form at all — a captain's `teamId` is on the **actor**, off a `memberships` row, so there is no claim to check because there is no read here that could return another team. `TeamOwnView` carries no other team, no score and no bid code but its own: a competitor holding the name-to-code mapping is the end of blind judging for that comp, arriving from inside the product rather than from the street, and `scope.test.ts` asserts it at the type level.

`listDutiesForLiaison` is the fifth, and it clears the same bar: the first three answer *which teams count for this board or this judge*, the fourth answers *what does my team owe*, and none of them can answer ***what am I supposed to be doing, and when*** — whose subject is not a team at all. C1's first draft argued it was **not** a window, on the grounds that scope comes off the actor and no id arrives from a form. **That argument does not survive its own precedent**: `ownTeamForCaptain` takes no id either and is counted as the fourth, so *taking no id* is what makes a window **safe**, not what keeps it **uncounted** — and once a liaison can acknowledge a duty an `assignmentId` genuinely does arrive on a form. It is safe for the same pair of reasons the fourth is: scope is `actor.personId` off a `memberships` row, so no read here could return somebody else's duty; and the write's `assignmentId` resolves one level down this read, `releaseAllocation`'s shape, where the array holds only live unrevoked rows. `DutyView` carries **no `bid_code`**, asserted at the type level — a liaison holds the name of the team they are walking, and the code beside it would end blind judging from inside the product exactly as a captain's would.

All five are in `src/lib/auth/scope.ts`, and the three original ones go through `claimed()`. The scoring windows filter to `SCOREABLE_STATUSES`; the roster window deliberately does not, because registration has to manage the applied, the waitlisted and the dropped — a screen that hid them could not accept a team. **Do not add a sixth window, and do not write a check outside one.** `addDeductionAction` is what a *missing* one cost: `scores.team_id`, `judge_notes.team_id` and `deductions.team_id` are all bare FKs, so the database takes the row happily and `tabulate()` then filters it back out of the arithmetic — the write succeeds, the actor is told it worked, and it counts for nothing. A deduction that silently does not apply is worse than one that fails.

**A link can be killed; nothing mints one** ([ADR-0011](docs/decisions/0011-nothing-mints-a-link.md)). Both `judge_assignments.revoked_at` and `board_assignments.revoked_at` are now written, not just read. Board revocation stays available **after** the lock (a board link is the one that can still override) and refuses the **last** live link (nothing issues a replacement, and a reseed destroys the scores).

**A `BoardActor` has two origins and exactly one function knows it** ([ADR-0022](docs/decisions/0022-a-link-is-exchanged-for-a-cookie.md)). `resolveBoardAccess(compId)` in `src/lib/auth/access.ts` tries the account session first — `resolveSessionUser` then `membershipFor(personId, compId, "board")` — and falls back to a board-link cookie. Everything downstream takes the actor and cannot tell which, which is the point: three windows, twenty writes and every `audit_log` row are unchanged, and `boardAssignmentId` went nullable rather than anything branching on it. **The link path must assert `actor.compId === compId`, and that one line is the security of the whole arrangement**: `membershipFor` is scoped by construction, a token is not — `resolveBoardActor` resolves whatever assignment the token names, at whatever comp it belongs to, so without the check a board member at one comp reads another org's roster by editing a slug. `e2e/scope.spec.ts` drives it against a real second comp.

`access.ts` is separate from `scope.ts` for a mundane, load-bearing reason: `scope.ts` is imported by `src/db/doctor.ts`, which runs as a CLI with no request behind it, and `next/headers` there breaks the preflight at import time. **Board forms carry two fields and they are not one field**: `compId` authorizes, `basePath` only addresses a `revalidatePath`. One string doing both jobs would be trusted for the second reason on the day somebody needed it for the first.

**The URL names a place; the cookie says who you are.** Screens live at `/app/[org]/[comp]/…`; `/board/[token]/[[...rest]]` is a route handler that exchanges the token for an `HttpOnly` cookie and redirects — ADR-0003's own unfinished hardening, and what keeps every emailed link working. It is a route handler because Next 15 forbids a Server Component setting a cookie. **It mints nothing** (ADR-0011): same `board_assignments` row, same `revoked_at`, shorter-lived carrier.

**Accounts are the minting path, and a judge still has none** ([ADR-0016](docs/decisions/0016-accounts-for-people-who-stay-links-for-people-who-visit.md)). ADR-0011 refused to mint a link and named its own successor — *"issuing a credential to a person for a comp is board management, and that is the thin end of Module A"* — and P1 is that. The rule is **accounts for people who stay, links for people who visit**: board, captain and liaison sign in; a **judge does not**, because a judge scores once as a favour and an account is friction charged to a volunteer. ADR-0003's no-install argument was always an argument about somebody who uses the product exactly once, and that is only true of judges. Both models coexist and no existing link was invalidated. An invitation names **who it is for** before it is accepted, so accepting one cannot make you somebody else, and `invitations_live_unique` is partial over the unspent rows so a re-invite supersedes rather than leaving two valid envelopes in the world. Do not add a self-serve signup: being on a comp is something a board decides.

`ACTOR_KINDS` is one definition and `audit_log_actor_kind_check` derives from it, so a new kind of actor is a **migration** rather than a type edit — the right friction for the column recording who did what.

**Writes stay on neon-http; a transaction is the exception, not the upgrade** ([ADR-0012](docs/decisions/0012-transactions-for-writes-that-span-statements.md)). `db` has no transactions and that is the fact the whole locking design rests on. `withTransaction` exists for writes whose invariant spans two statements — today that is **exactly four callers**, and the first two were named in ADR-0012 before either arrived. The **roster**, where a roster fact and the obligations it implies must land together; the **ledger** (`src/lib/money/ledger.ts`), where a payment row, its allocations and the counter that constrains them are one act — half of it is a payment nobody can see the destination of, or a counter claiming $2,160 is spent when nothing is; and the **deposit ending** ([ADR-0015](docs/decisions/0015-a-refund-moves-the-money.md)), where a deposit's terminal event and the money it returns land together — half of it is a deposit marked `refunded` while the team still reads as owing it, or an obligation quietly voided with nobody recorded as having decided anything.

**Callers are counted by invariant, not by call site**: `recordPayment`, `allocatePayment` and `releaseAllocation` are all the ledger's, and `setTeamStatus`, `setTeamBilling` and `regenerateCharges` are all the roster's — a status, a dancer count, a room count and a comp-wide regeneration are four ways of saying *this is what the roster claims, and this is therefore what is owed*. And **accepting an invitation** ([ADR-0016](docs/decisions/0016-accounts-for-people-who-stay-links-for-people-who-visit.md)), where an invitation is spent exactly when the authority it grants exists — half of it is an envelope marked used that granted nothing, or a membership with no account behind it. That is why the count is four while `grep` finds eight. `releaseAllocationsForCharges` takes the caller's `Writer` and opens nothing, and `advanceDeposit` opens one **only** for the terminal `refunded` move: the non-terminal states are one INSERT, and *this deposit is now pending* implies nothing else. A fifth *caller* needs the same argument made again: an invariant that genuinely spans statements, not a write that merely has several.

**A message sends once, a unique index says so, and the outbox is deliberately not a fifth caller** ([ADR-0020](docs/decisions/0020-a-message-sends-once.md)). This is the first thing the product built that acts on the outside world, and it changes what correctness means: every earlier write was a row a board could correct, and there is no `revoked_at` on somebody's inbox. So `messages_comp_dedupe_unique` over `(comp_id, dedupe_key)` is the guarantee, and a caller never asks whether it already sent — it inserts and reads the refusal, because the ask and the insert are two acts and only the index is atomic. **A duplicate is not an error**: `reason: "duplicate"` is what a board clicking twice looks like, and the screen says *already sent* rather than showing red. The dedupe key is the caller's sentence about what the message *is* (`dues:2027-02`), never a digest of the body — a digest makes a reworded reminder a new message and sends it again, which is the bug. `messages.state` is denormalized and **is** the claim, so claiming is one guarded `UPDATE`, `releaseAllocation`'s shape; `failed` is retryable and `bounced` is not; and a message stuck in `sending` is **reported and never auto-retried**, because that is the crash-after-send footprint and retrying it emails somebody twice.

Four rules travel with it. **Suppression is decided at send and by kind, never by recipient** — `people.unsubscribed_at` bounces a broadcast and delivers a bill, because a debt is owed whether or not somebody wants to hear from the board; and the opt-out must be *reachable*, which means a visible line in the body and not only a `List-Unsubscribe` header, off **one** field on the payload so the two cannot disagree. **Who a message is addressed to has one definition**, `contactPersonFor` — a registered contact wins, a captain's membership is the fallback, and that fallback is the only contact a founder-seeded roster has at all. **A template is pure and its payload is typed per template**, because the compiler is the only thing that will notice a body reading a field the caller never sent, and *you owe $undefined* is exactly the wrong number this product exists not to produce. And **a payload holds a credential only until it sends** ([ADR-0021](docs/decisions/0021-the-outbox-holds-a-secret-only-until-it-sends.md)): `SCRUBBED_FIELDS` is the one declaration of which fields those are, it has one entry, and a template added with a secret in it and nothing there is the leak.

**Queue after the transaction, never inside it.** A receipt is a consequence of a payment, not part of it — enqueueing inside `recordPayment`'s transaction means a comms failure rolls back money that genuinely arrived, which is this product's own headline defect caused by the feature announcing it. Same for the deposit return and the roster.

`setTeamStatus` has **no non-transactional path left**, and that is a deliberate loss. It used to take a single statement when a move promoted nobody, which was correct until accepting a team also had to generate what it owes: `applied → accepted` is now *"accepted **and** owing what the schedule says"*, and half of that is an accepted team owing nothing — the orphan A3 exists to prevent. Its guards stay **outside** the transaction, because a refused move must not pay for a WebSocket handshake. **Do not migrate `lockResults` onto it.** `tab_runs`' chain indexes refuse a fork from code that never opens a transaction, from a seed script, from a hand-typed `INSERT`; a transaction only protects the code that remembers to ask.

**The roster freezes at the lock.** `teams` lives inside `tab_runs.inputs`, so a roster that moved after a lock describes a comp the locked result does not. `transitions.ts` permits `dropped → accepted` (registration churn runs for months, and a board must be able to un-drop a mistake) **only because `setTeamStatus` refuses every transition once a run exists.** Reinstating a dropped team after a lock would hand it back the scores it had already been given — ADR-0009's bug, through a new door.

**Every query is scoped.** Data access goes through `src/lib/auth/scope.ts`, which requires an `Actor`. There are exactly **three** exceptions, all public, all `Actor`-less because the reader is nobody, and all governed by the same rule: **the projection *is* the scope.** The third is `listOpenComps` (`src/lib/comp/open.ts`), the front page's read — org and comp name, slug and date for comps at `status = 'open'`, and **no count of teams**, because how many have applied is a fact about a board's season that a rival board should not read off a public page. It was added under this file's own instruction that *adding a third public read means adding a third projection, not relaxing one of these two*, and that is what it did.

`compIdBySlugs` and `compSlugsById` in `access.ts` are **lookups, not windows**: they take no actor, return an id or two slugs, and every caller's next act is to prove the holder may open it. A function in `lib/auth` that takes no `Actor` is exactly the shape somebody should flag on review, so it is said here rather than left to be rediscovered. `openRegistration` is the public form's read and selects no team, no score, and no person. `publicComp` (ADJ·3, `src/lib/comp/public.ts`) is the attendee page's, and it selects **no `bid_code`, no score, and no team that is not competing** — a judge is a member of the public, so a page carrying names *and* codes would hand the panel the mapping ADR-0008 exists to withhold. Both enforce it in the return type, where re-adding a field is a compile error rather than a review someone has to pass. Adding a third public read means adding a third projection, not relaxing one of these two. `openRegistration` now joins `fee_schedules` for one boolean — whether the comp bills per room, and therefore whether the form asks for a room count — which is the rule working rather than bending: it selects a comp-level fact a stranger is being asked to answer anyway, no team and no person, and it is derived rather than declared a second time in `comps.registration` so the question and the charge cannot disagree. Blind judging is enforced here: a `judge` actor resolves a team to its `bid_code`, a `board` actor to its `name`. A `teamId` arriving on a form is a claim, not a fact — check it against the scoped read that produced the form (`listTeamsForJudge` / `listTeamsForBoard`) before writing a row against it. `scores.team_id` is a bare FK, so the database will not catch a team from another comp.

**`teams` is the roster of record; a score is only evidence about it** ([ADR-0009](docs/decisions/0009-teams-is-the-roster-of-record.md)). Placements are driven by the scores, so a score naming a team not in `TabulationInput.teams` is ignored — otherwise a team that withdrew keeps the scores it was already given and goes on placing with them, above the teams that did compete. `tabulate()` filters for this itself, and that filter is **not** redundant with the query that loads it: it is what makes the function hold its contract for a snapshot replayed a year later. `SCOREABLE_STATUSES` has one definition, in `src/db/schema/teams.ts`. Do not write a second one.

**Every board action is attributed.** `BoardActor.personId` is non-nullable, because board links are per person (`board_assignments`), not per comp. Do not add an anonymous board path — `tab_runs.locked_by_person_id`, `deductions.created_by_person_id`, and `audit_log.actor_person_id` were all null before it, which made PRD B6's "attributed override" false.

**A comp is one division** ([ADR-0010](docs/decisions/0010-a-comp-is-one-division.md)). One rubric, one judge pool, one ranked list. Nothing downstream is division-aware and nothing should be: a board running two divisions gets two comps, which is what they are. `parseCompConfig` refuses a config declaring a second division — that is the only door, so it is where the refusal lives. `judge_assignments.division` was **dropped**: it read like an authorization key ("which teams may this judge see") and authorized nothing. `teams.division` stays because it only describes. Do not add a division column back without making the judge's window honor it.

**A seed replaces a comp, not an org** ([ADR-0013](docs/decisions/0013-a-seed-replaces-a-comp-not-an-org.md)). `seedFromConfig` deletes by `(org_id, comp.slug)`; `orgs` and `people` are found-or-created and never deleted. This is what makes "two divisions are two comps" survivable in practice — it deleted by org slug before, so a founding partner who followed INTAKE.md and sent their second division had their first one destroyed by the seeding of it. `people` is org-scoped and survives the comp delete, so it must be **found**, not re-inserted: `people_org_email_unique` refuses the second insert, and every reseed of the demo runs through that path. `liveLinksAtRisk` counts the target comp only — counting the org would refuse the seed that creates a sibling division. Nothing mints a link, so a seed is still the only way to issue one, and reseeding a comp still kills the links already handed out.

**A comp's runs are one chain: one root, one head.** `tab_runs_root_unique` and `tab_runs_supersedes_unique` are both partial indexes and both load-bearing — the first refuses a second first-lock, the second a second override. Neither is redundant. `lockResults` checks before it inserts, but neon-http has no transactions, so the check and the insert are two acts and two board members can land between them; the database is the only thing that can actually refuse a fork. If a lock path catches a DB error, read `error.cause.constraint` — drizzle's own `message` is the failed SQL, and a board member must never be shown it.

Because the guarantee lives in the database rather than the code, **the code cannot assume it is there.** `db:doctor` looks both indexes up in `pg_indexes` and reports a comp with two roots by id — that is what makes the preflight mean "this database enforces the invariant", not merely "this demo is seeded". Reseeding is never offered as the remedy for either: it does not create an index, and it does not decide which of two locked results stood. Their names have one definition, `CHAIN_INDEXES` (and the `CHAIN_INDEX_NAMES` derived from it) in `src/db/schema/scores.ts`, because the schema, the lock path, and the doctor must agree on the strings and none can derive them. Do not write a second one — and note the *DDL* has one definition too, in the migration: `e2e/doctor.spec.ts` drops an index only after capturing `pg_get_indexdef`, and restores it by replaying what Postgres handed back.

**Merging is not deploying, and deploying is not migrating.** Vercel ships code on a merge to `main`; nothing applies the migration, so after merging anything that adds a file to `drizzle/`, run `db:migrate` against `main` and then the preflight. From July 13 to August 1, 2026 that was not done: `main` sat at `0006` under code expecting `0010`, and every Module A screen plus ADJ·3 returned 500 for nineteen days while three waves of work merged green. `db:doctor` therefore counts applied migrations against `drizzle/meta/_journal.json` — the two older database checks are constraint-shaped and `0007`/`0008` add no constraint, so nothing could see them missing — and prints the compute it just checked, because the preflight that would have caught this on day one was pointed at `dev` and printed the same green line. **A verdict without its subject is what made a working instrument useless.**

**`db:doctor` reads configuration as well as the database, and an absence is a caveat while a contradiction is a hazard.** The verdict lives beside `ok`, never inside `problems` — `db:seed` gates on `ok`, so a config fact landing in the problem list would mean a missing `RESEND_API_KEY` refuses to seed a demo. A caveat exits 0 everywhere, including production, because production having no sending credential is deliberate and documented and a preflight that goes red for it is one that gets skipped before a call. A hazard exits 1 everywhere, including a laptop, because it is a fact about the *process environment* rather than about whichever database was named — so no `isProtectedDatabase` branch decides it. `CRON_SECRET` set while sending is off is the hazard that matters: the sweep marks the queue sent through a transport that sends nothing, `scrubPayload` destroys the invitation links, and `messages_comp_dedupe_unique` then refuses to re-enqueue any of it. That order is stated in the caveat block *before* it can be got wrong, because there is no `revoked_at` on somebody's inbox. `readConfigEnv` in `src/db/config-env.ts` is the one definition of the env read, shared by the CLI and `/api/health` so the two cannot drift, and it never re-derives `sendingConfigured` / `driveConfigured` / `sealingConfigured` — it adds only the tri-state those booleans cannot express.

**`/api/health` is a fourth `Actor`-less route, and it is not a fourth public projection of product data.** It carries a migration count and which integrations are configured — no org, no comp, no team, no person, no money, and no value read out of `process.env`, only whether one is set and, where it is unset, its name. It exists so CI can ask production how far along it is **without a production database credential in GitHub Actions**: the process that already legitimately holds `DATABASE_URL` does the reading. `force-dynamic` and `cache-control: no-store` are both load-bearing rather than stylistic — `next build` runs against a fake `DATABASE_URL` on the premise nothing here is statically rendered, and a cached health endpoint is a green check that is a lie about a fact that changed. Its payload is `HealthPayload`, one definition, and it is **parsed rather than cast** on the way back in, because a typo'd URL answering somebody else's JSON must not produce a confident verdict. `compareMigrations` is a shared *sentence*, not a shared policy: `db:doctor` skips `unknown`, and `db:migration-check` fails on it.

**`db:doctor` splits pure from observed, and both halves need testing.** `summarizeHealth` in `src/db/health.ts` is pure and unit-tested; `src/db/doctor.ts` is what reads the database, and a wrong index name or a broken `GROUP BY` there would leave every unit test green while the doctor passed a database that can still fork a locked result. `e2e/doctor.spec.ts` drives each failure branch against a database actually in that state. It breaks the database and repairs it in a `finally` — and order matters: the fork must be cleared **before** the unique index goes back on, because it cannot be built over rows that violate it.

## Code style

Follows the global CLAUDE.md. Specifically enforced by ESLint here:

- No `any`. No `enum` — string literal unions.
- `type`, not `interface`.
- Functional. No classes.
- Tests live in `__tests__/` next to the source.
- No comments that restate the code. Comment only constraints the code cannot express.

## Testing

The acceptance bar is written in PRD §8.3 and encoded in `e2e/scoring.spec.ts`: 8 teams, 3 judges, phones, locked auditable placements in under ~5 minutes, reproducible the next day.

`src/lib/tabulation/__tests__/reproducibility.test.ts` is the one test that must never be weakened. It re-runs `tabulate()` against a stored snapshot and asserts deep equality. If it fails, the audit trail is a lie.
